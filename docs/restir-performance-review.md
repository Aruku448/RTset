# ReSTIR 性能实现检查（2026-10-07）

本报告记录优化前的代码审查。随后已实现前缀保存/续追、同次执行的主射线与次级射线命中缓存，以及DI选中目标缓存；见 restir-implementation.md 的 Prefix continuation optimization。下表的完整路径重跑和两次重复目标评估已处理，历史失效、显存和几何重连接问题仍存在。

原审查结论：当前直接光照模式是用额外候选计算换取采样质量；后缀模式是完整路径重放实验，尚未实现低消耗后缀复用。开启不等于加速。此次为代码和已有运行日志检查，没有固定场景 A/B GPU 基准，也未修改实例参数。

## 主要发现

| 优先级 | 位置 | 发现及影响 | 优化方向 |
|---|---|---|---|
| 高 | RayTracingRestirShader.java:235–248 | 每个接受的历史后缀都会调用完整 runRestirPath。默认 prefixes=1、neighbors=2 时最多执行4次；当前 neighbors=3 时最多5次；参数上限为24次。主射线、主表面材质、太阳/月亮/天空/发光物阴影都重复计算。实际倍率取决于候选通过率、路径早停，不能等同为耗时倍率。 | 首先拆出并保存当前帧前缀，仅从次级交点重放。随后实现论文几何重连接、路径顶点存储和 Jacobian；需要相应支持域与估计器验证。 |
| 中 | RayTracingRestirShader.java:118–163 | 原积分器主表面仅抽1个发光候选；DI默认抽4个，还评估最多3个历史候选及2次选中目标。默认最多9次目标评估，而非减少到更少候选。有效选中灯光仍需新遮挡查询。 | 缓存选中目标，消除2次重复评估；按相同噪声水平而非相同采样数比较质量/时间。原实现已只有一个主表面发光NEE样本，不能声称减少其阴影射线。 |
| 中 | RayTracingVulkanPass.java:2080–2083；RestirLayout.java:7、25 | 每次静态几何发布都会清空全屏历史；每8帧也会全局清空。最新会话有134条场景发布记录，区块加载时复用容易中断。几何失效目前防止光源索引变化，不能直接删掉。动态BLAS/TLAS更新本身不等于该静态发布。 | 为光源建立稳定身份/版本、区分接收面和光源变化，再细化失效范围；保留支持域和可见性检查。 |

另有材质、BLAS/TLAS、NRD、FSR和大气资源。这些是Vulkan缓冲占用，不等同于Java堆。已有全系统OOM事件不能仅凭这些缓冲判定由ReSTIR造成。

## 已做对的部分及额外开销

- 候选目标不逐个追踪阴影，只对最终有效DI样本执行新可见性检查；动态阴影分离可能额外查询静态可见性。
- 关闭模式及DI单独模式有编译专门化，不承担后缀重放路径；缓冲尺寸稳定时没有逐帧重新分配。
- 历史读取与当前写入使用不同银行，交换和写入依赖已建立。历史失效不是当前帧并发邻域复用。
- 模式开关会重建RT资源，包括FSR和管线，会有一次性卡顿；同模式参数变化只清历史。
- 开启期间每帧更新2个储存缓冲描述符并映射32字节参数，属于CPU开销；是否值得优化需测量，不应先认定它是瓶颈。
- legacy RGB体积路径在DI开启时独立采样体积灯光并重新检查遮挡，增加工作，但避免把reservoir的UCW当普通生成PDF使用；不能直接恢复旧可见性复用。
- 主表面DI在后缀重放中也会被重复评估，因此两个开关同时开启时成本叠加。

## 已有运行证据及限制

最新日志确认模式0/1/2/3都进入了运行端。2560×1404双模式曾记录RT约35.636–79.237 ms（部分帧）；1706×936双模式记录25.815 ms，直接模式另一次记录44.668 ms。这些会话的视角、场景、历史、分辨率和参数没有固定，不能作为DI更慢或双模式更快的因果证据，也不能证明优化收益。

建议后续验证：固定相机、场景、RT分辨率、GI、NRD和太阳样本数，分别测关闭、DI、suffix、both；等待区块发布结束并预热，记录GPU中位数/P95及时间/空间候选接受率、历史失效次数和实际重放数。用同一参考图量化误差，再比较相同质量下的GPU耗时。

优化顺序：保存前缀与主表面照明 → 避免DI重复目标评估 → 稳定光源身份并细化历史失效 → 几何重连接与储存压缩。当前“低消耗可选路径”目标尚未由后缀实现满足。
